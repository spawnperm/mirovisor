# ADR-002: Асинхронная телеметрия и очереди сообщений на базе NATS JetStream

## Статус
Принято (Accepted) · 2026-10-12

## Контекст
Платформе Mirovisor требуется надёжный, высокопроизводительный механизм передачи телеметрии (`BuildCompleted`, `SecurityFindingDetected`, `TenantEvent`), оркестрации AI-агентов Cordis и обновления Канбан-доски в реальном времени.

Рассматривались альтернативы:
1. **RabbitMQ**: Высокое потребление памяти при росте очередей, сложная кластеризация.
2. **Apache Kafka**: Чрезмерный оверхед (JVM, Zookeeper/KRaft, сложный ops).
3. **NATS JetStream**: Сверхнизкая задержка (<1мс), минимальное потребление ресурсов (Golang бинарник ~20MB), встроенная персистентность (Stream Storage), семантики At-Least-Once / Exactly-Once, мультитенантные аккаунты (Accounts & Subjects).

## Решение
Принять **NATS JetStream** в качестве единого брокера событий и телеметрии платформы:
- Тематическая структура: `mirovisor.{tenant_id}.telemetry.{event_type}`
- Хранение потоков: File-based Stream Retention с репликацией R=3 для продакшн-окружения
- Идемпотентность: Deduplication window 2 минуты по `Nats-Msg-Id` (UUID события)
- Гарантия доставки: At-Least-Once с подтверждением `ack()` консьюмерами.

## Последствия
### Положительные:
- Пропускная способность >1,000,000 сообщений/сек на одном узле.
- Встроенная изоляция тенантов через NATS Accounts / Subject authorization.
- Нативная поддержка CloudEvents 1.0 JSON payloads.

### Риски и митигация:
- Риск рассинхронизации двойной записи (Dual-write) между БД и NATS решается внедрением Transactional Outbox Pattern в PostgreSQL.
