# Правила разработки проекта «Мировизор» (Mirovisor Development Rules)

> **Критическое правило разработки:**  
> **Каждая успешная сборка проекта должна завершаться автоматическим созданием Git-коммита.**

---

## 1. Автоматический коммит при успешной сборке (Auto-Commit on Build)

1. **Триггер коммита**:
   - При успешном завершении сборки (`npm run build` / `npm run build:commit` / `postbuild`) скрипт автоматизации проверяет статус рабочего дерева Git.
   - Если обнаружены измененные, добавленные или удаленные файлы, они автоматически индексируются (`git add -A`) и фиксируются коммитом.
2. **Условия допуска к коммиту**:
   - ✅ Сборка TypeScript и Vite завершилась с кодом возврата `0` (`npm run build`).
   - ✅ Все unit- и интеграционные тесты завершились успешно (`npm test` — Vitest).
   - ✅ Отсутствуют ошибки статического анализа и линтинга (`npm run lint` / `tsc --noEmit`).
   - ❌ Ни при каких условиях не коммитить код, если сборка или тесты завершились с ошибкой.
3. **Автоматический механизм**:
   - В `package.json` настроен хук жизненного цикла npm:
     ```json
     "scripts": {
       "build": "vite build",
       "postbuild": "node scripts/auto-commit-on-build.mjs",
       "build:commit": "npm run test && npm run build"
     }
     ```
   - Скрипт `scripts/auto-commit-on-build.mjs` анализирует затронутые файлы и генерирует семантическое сообщение коммита по стандарту Conventional Commits с суффиксом `[auto-build]`.

---

## 2. Стандарты коммитов (Commit Message Convention)

Все коммиты должны строго следовать стандарту [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>(<область>): <краткое описание в повелительном наклонении>
```

### Допустимые типы:
* `feat`: Новая функциональность (например, визуализатор D3.js, модуль CRM, автосохранение).
* `fix`: Исправление бага или регрессии.
* `perf`: Оптимизация производительности (кэширование, виртуализация, дебаунсинг).
* `test`: Добавление или обновление тестов (юнит, интеграционные, e2e).
* `refactor`: Изменение кода без изменения внешней логики.
* `docs`: Обновление документации, архитектурных схем, правил разработки.
* `sec`: Исправление уязвимостей безопасности, ротация ключей, ASVS hardening.
* `chore`: Обновление зависимостей, скриптов сборки, конфигураций CI/CD.

### Примеры сообщений:
* `feat(visualization): implement real-time D3 force-directed graph for tenant-plugin topology`
* `feat(kanban): implement localStorage auto-save draft for card descriptions`
* `rules: document automatic commit workflow on successful build`
* `test(kanban): add auto-save debouncing and draft restoration tests`

## 3. Требования к качеству кода и архитектуре

1. **Типизация**:
   - Строгий TypeScript (`noImplicitAny`, строгая проверка типов).
   - Запрещено использовать тип `any` без исключительного обоснования.
2. **Изоляция мультитенантности**:
   - Любые манипуляции с данными должны учитывать идентификатор активного тенанта (`tenantId`) и контекст схемы (`schema`).
3. **Сохранность данных пользователя**:
   - Все формы и редакторы (описание Канбан-карточек, заметки, настройки) обязаны поддерживать устойчивость к сбоям через локальные черновики (`localStorage`) или CRDT-провайдер (`yjs`).
4. **Визуализации и графики**:
   - Сложные графы взаимосвязей компонентов должны реализовываться с использованием D3.js (v7) с поддержкой масштабирования, панорамирования, физической модели и реактивной фильтрации.

---

## 4. Безопасность и управление секретами

1. **Никаких секретов в Git**:
   - Персональные токены доступа (GitHub PAT), API-ключи, приватные сертификаты запрещено добавлять в историю коммитов.
   - Использовать переменные окружения (`.env.example`), секреты CI (`GitHub Secrets`) или серверное проксирование.
2. **Автоматический аудит зависимостей**:
   - Каждый релиз и PR проходит проверку сканерами уязвимостей (`npm audit`, Trivy, OWASP Dependency-Check).

---

## 5. Чеклист перед каждым релизом

- [ ] `npm run lint` — 0 ошибок
- [ ] `npm test` — все тесты пройдены
- [ ] `npm run build` — сборка успешна, сработал автоматический коммит
- [ ] Рабочее дерево Git чисто (`working tree clean`)
